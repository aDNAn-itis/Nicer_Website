### Problems with Simple Caching at Scale

**Problem 1: Django's Default Cache (LocMemCache) is Per-Process**
In production, Django runs with multiple worker processes (e.g., Gunicorn with 8 workers). Each worker has its **own separate memory cache**. So:
- User A hits Worker 1 → computes plot → cached in Worker 1's memory
- User B hits Worker 2 → Worker 2's cache is empty → computes again
- You get **8 separate caches** that never talk to each other. Useless at scale.

**Problem 2: Memory Explosion**
NICER has thousands of observations. If 500 different users load 500 different obs_ids, and each Plotly HTML is 5MB → **2.5GB of RAM** just for the cache. The server runs out of memory.

**Problem 3: The Thundering Herd (Cache Stampede)**
If a popular paper gets published about Serpens_X-1 and 300 astronomers all visit the site at the same time, and the cache is empty → **300 simultaneous full plot computations** hit the server at once. Server dies.

---

### The Right Architecture for Production Scale

The fix has **two layers**:

**Layer 1 — Use Redis as a Shared Cache (Not Local Memory)**
Redis is a single, shared cache server that **all** Django worker processes talk to. User A hits Worker 1 → cached in Redis → User B hits Worker 2 → Redis has it → instant response. This is the standard production solution.

**Layer 2 — Cache the Intermediate Numpy Data, NOT the Full HTML**
Instead of caching 5MB Plotly HTML strings (which kills memory), cache the small intermediate computed arrays:
- `time[]`, `hardness[]`, `intensity[]` for HID

### 2. "What if 1000 people use this website at the same time?"
You are absolutely right. If 1000 people load 1000 *different* obs_ids that aren't in the cache yet, the server will try to do 1000 × 10 seconds of CPU rendering all at once. **The server will crash.**

If you are expecting 1000 concurrent users, **we cannot generate plots when the user clicks the button.** The only true fix for production at that scale is **Offline Pre-computation**.

### The "Real" Ultimate Fix (Pre-computation Architecture)
Instead of making the web server do the work while the user waits, we move all the heavy lifting to the background:

1. When Ethan runs `db_update.py` to add new NICER data, we add a script at the end called `generate_all_plots.py`.
2. This script loops through every single observation in the database, generates the Plotly HTML strings, and saves them permanently to the database (or as `.json` files on the disk). This might take 5 hours to run, but it happens completely offline.
3. When your 1000 users visit the website, `views.py` does **zero math and zero rendering**. It just says: *"Fetch the pre-made HTML string for Serpens_X-1 from the database and send it."* 

Load time becomes **0.05 seconds** for every user, every time, permanently.
